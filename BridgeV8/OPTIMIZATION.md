# BridgeV8 최적화 기록

BridgeV7의 게임·학습·개발자 UI·샌드박스·배경 그래픽·Gemini 기능을 복사하고 반복 탐색과 임시 배열 생성을 줄였습니다. 화면 표시 버전은 `project-settings.json`의 `display_version: "V8.0.0"`입니다. 캠페인과 체인지로그 내용은 원본을 유지합니다.

## 실행

프로젝트 최상위 폴더에서 실행합니다.

```powershell
python -m http.server 8765 --bind 127.0.0.1 --directory BridgeV8
```

브라우저에서 `http://127.0.0.1:8765`를 엽니다. 기존과 같이 화면 폭 1100px 이상이 필요합니다. Gemini Worker는 기존 주소를 사용하며 이번 최적화를 위해 서버를 변경할 필요는 없습니다. 동일한 브라우저·origin에서는 V7과 진행도 및 설정 저장 키를 공유합니다.

## 변경한 부분

- **관절 조회:** 그리기·정적 해석·붕괴 계산 한 번의 동기 실행 안에서 ID 조회용 Map을 재사용합니다. 실행이 끝나거나 오류가 발생하면 이전 조회 상태로 복원합니다. 편집·관절 교체·단계 변경 이후에는 새 Map을 만듭니다.
- **삼각형 집계:** 모든 관절 세 개의 조합을 검사하던 방식에서 실제 연결된 이웃끼리 검사하는 방식으로 바꿨습니다. 기존의 사용자 부재·표시 관절 조건과 중복 없는 집계 기준을 유지합니다.
- **지지 경로:** 도로 관절마다 별도 탐색하던 방식을 양쪽 지점에서 한 번 탐색하는 방식으로 바꿨습니다. 도로를 제외한 부재와 끊어지지 않은 케이블의 연결 조건을 유지합니다.
- **도로 탐색:** 정적 해석의 여러 차축이 같은 도로 도달 가능 집합을 재사용합니다. 해당 해석이 끝나면 버립니다.
- **행렬 생성:** 자유도별 임시 일반 배열과 추가 복사를 줄이고 Float64Array에 직접 기록합니다.
- **선형 연립방정식:** 반복문 안에서 같은 행을 재조회하지 않도록 행 참조를 재사용합니다. 피벗 선택, 계산 순서, 불안정 판정 임계값은 유지합니다.

물리 상수, 하중·휨·좌굴·파단 계산식, 차량 충돌 조건, 시간 간격, 그래픽 품질과 UI 이벤트는 그대로 사용합니다. 폴리곤이나 화면 효과를 줄여 얻은 결과가 아닙니다.

## 비교 검증

- 정적 해석 41개 사례: 차량 종류, 일반·강화 도로, 두 차량, 바람, 하중 위치, 끊어진 도로와 관절 편집·삭제·단계 재설정을 비교했습니다. 변위·부재력·이용률·반력·결과 판정이 허용 오차 `1e-9 × max(1, |V7|, |V8|)` 이내로 일치했습니다.
- 난수 연결 그래프 40개 및 관절 순서를 뒤집은 사례: 삼각형 수, 도로 도달 집합, 지지된 관절 집합이 일치했습니다.
- 붕괴 4개 사례: 동일한 시간 간격과 난수 조건에서 관절 궤적·차량 상태·파단·조각을 비교했습니다. 도로만 있는 18kN 하중 사례에서는 양쪽 모두 부재 3개가 끊어지고 조각 6개가 만들어졌습니다.
- 완주 사례: 양쪽 모두 차량 통과, 충돌 없음, 파단 없음으로 끝났습니다.
- 같은 설계·카메라·시각에서 Canvas PNG가 바이트 단위로 같았습니다. 한 비교 장면에 대한 검증입니다.
- Gemini 요청의 구조 정보·설명 수준·설정 저장, 마크다운 표시·ID 설명 치환·오류 처리·대화 초기화를 모의 서버로 확인했습니다. 작은 화면에서도 AI 입력부가 가려지지 않았습니다.
- 생성 전 기록한 BridgeV7의 모든 파일 해시를 다시 비교해 원본 파일이 유지됐는지 확인합니다.

## 실행 시간 측정

동일한 로컬 Edge 헤드리스 환경에서 준비 실행 후 V7/V8 순서를 번갈아 다섯 번 측정한 중앙값입니다. 각 수치는 함수 한 번당 시간입니다.

| 작업 | 테스트 설계 | V7 | V8 | 시간 기준 속도비 |
| --- | --- | ---: | ---: | ---: |
| 삼각형 집계 | 관절 121개·부재 239개 | 3.917ms | 0.075ms | 약 52.2배 |
| 지지 경로 탐색 | 관절 121개·부재 239개 | 0.345ms | 0.028ms | 약 12.5배 |
| 정적 해석 전체 | 관절 81개·부재 159개, 두 트럭 | 2.175ms | 1.513ms | 약 1.44배 |
| Canvas 그리기 | 관절 121개·부재 239개 | 6.725ms | 6.725ms | 사실상 동일 |

이 표는 해당 테스트 입력과 환경의 CPU 실행 시간입니다. 전체 FPS나 GPU 사용량의 개선 배수를 의미하지 않으며, 작은 설계에서는 차이가 작을 수 있습니다. 기존 밀집 행렬 해법을 사용하므로 매우 큰 설계의 선형 해석 비용은 여전히 관절 수에 크게 영향을 받습니다.
